# 03 三人分工与集成计划（可执行版）

> 本文是小组内部的实施分工，不是课件原文。A、B、C 分别对应三位同学；交作业前填入真实姓名和学号，并按实际完成情况更新贡献记录。功能范围以 [01 需求与范围](01-requirements.md) 为准，跨模块数据类型和函数签名以 [02 架构与接口](02-architecture-and-interfaces.md) 为准。

**状态说明：** 下方里程碑和“第 0 步”描述的是项目初期计划。当前三模块与桌面界面已集成；实际操作请使用[完整使用手册](09-user-manual.md)。

## 1. 总目标和责任边界

最终程序要形成完整链路：`SQL 输入 → 解析与检查 → 查询计划 → 执行 → 存储/索引 → 缓存 → 磁盘 → 返回结果`。每人负责链路中的一段，也负责该段的测试和实现说明。

| 成员 | 模块所有权 | 必须交付 | 不负责的事情 |
| --- | --- | --- | --- |
| A：存储与缓存 | `dbms/storage/`、`tests/unit/test_storage*.py` | catalog、堆文件、页编码、缓存、索引、`StorageEngine` | SQL 解析、输出格式、执行计划解释 |
| B：SQL 前端与界面 | `dbms/frontend/`、`dbms/__main__.py`、`tests/unit/test_frontend*.py` | tokenizer、parser、语义检查、计划选择、交互/脚本 CLI、使用说明 | 直接读写数据文件、执行行过滤 |
| C：执行与集成 | `dbms/executor/`、`tests/unit/test_executor*.py`、`tests/integration/`、`examples/demo.sql` | `execute`、谓词/投影、增删改执行、集成测试、演示脚本、合并协调 | 私自改存储格式或 SQL 语法 |

`dbms/types.py`、`dbms/contracts.py`、需求/接口文档属于**共享契约**，接口基线 v1 已建好。A、B、C 直接导入这些类型；如需修改，应同步更新契约、02 文档和相关测试并通知其他成员。A、B、C 均需参与最终报告审阅。C 负责组织集成，不意味着替 A/B 完成其模块；若实际补位，须在贡献记录中写清楚。

### 工作量平衡

A 的磁盘页、缓存和索引工作通常最重。B 在解析器稳定后补充 SQL 边界测试和使用说明；C 在执行器稳定后承担端到端测试、演示材料和合并问题定位。优先保证各模块真正可运行，而不是用页面或报告工作代替核心实现。

## 2. 已完成的“第 0 步”：接口基线 v1

以下决定已经写入共享代码和文档，可直接执行；三人无需重新设计一遍接口。

1. 采用 Python 3.10+、标准库、命令行程序和本地文件；若老师另有技术要求，再更新文档。
2. SQL 子集、列类型、字符串转义、错误类型、`Result` 输出语义见 01/02 文档。
3. `StorageEngine`、`parse`、`plan`、`execute` 的签名与 `Statement`/`Plan` 字段见 `dbms/types.py` 和 `dbms/contracts.py`。
4. 运行入口固定为 `python -m dbms --db <数据库目录> [--file <脚本.sql>]`。
5. `dbms/storage/`、`dbms/frontend/`、`dbms/executor/` 已建立为可导入的包；对应负责人实现公开导出。

**第 0 步当时的交付：** 类型骨架、存储端口、能导入的包结构、行为约定。此阶段尚未实现数据库功能；后续里程碑已完成集成。

## 3. 成员 A：存储、缓存、索引

### A 的细分任务

| 编号 | 任务 | 具体产物 | 完成判据 |
| --- | --- | --- | --- |
| A1 | 元数据管理 | 创建/读取 `catalog.json`；记录表结构和索引定义 | 重启后表和索引元数据仍可读；重名报错 |
| A2 | 页文件与行编码 | 4096 字节页、槽目录、`RID`、`INT`/`TEXT` 编解码 | 插入、跨页扫描、删除标记正确；边界值不损坏 |
| A3 | 缓存管理器 | LRU、脏页、淘汰写回、`flush`、统计计数 | 小容量时能观测命中、未命中、淘汰、写回 |
| A4 | 表操作 API | `create_table`、`insert`、`scan`、`update`、`delete` | 返回值与异常符合 02 文档；关闭重开后数据正确 |
| A5 | 持久化等值索引 | 建索引时回填既有行；维护重复键及增删改 | `lookup_eq` 与全表扫描结果一致；重启后仍一致 |
| A6 | 模块测试与说明 | 存储单元测试、文件格式简述、限制说明 | `python -m unittest` 可在临时目录重复运行 |

### A 的对外承诺

- 只通过 `StorageEngine` 提供服务，不要求 B/C 理解页布局或索引文件。
- `scan` 返回所有当前有效行；`lookup_eq` 返回索引列等于指定值的当前行，并支持重复键。
- `update` 保持同一 RID；超过原记录空间时按 02 文档报错，不悄悄移动记录。
- 任何公开方法收到不存在的表/列或类型错误时使用约定异常，不直接 `print`。

### A 可独立验证的场景

用 Python 直接构造 `StorageEngine` 和 `TableSchema`：创建表 → 插入三行 → 扫描 → 建索引 → 查重复键 → 修改被索引的列 → 删除行 → `close()` → 重新打开并重复查询。另用容量为 2 页的缓存驱动至少 3 页访问，检查统计计数和脏页持久化。A 不需要等待 SQL 解析器。

## 4. 成员 B：SQL 前端、计划与用户界面

### B 的细分任务

| 编号 | 任务 | 具体产物 | 完成判据 |
| --- | --- | --- | --- |
| B1 | 词法处理 | 识别关键字、标识符、数字、单引号字符串、比较运算符、分号 | 字符串内的分号和转义单引号不被错误拆分 |
| B2 | 语法解析 | 六类 SQL 语句变成 `Statement` 数据类 | 01 文档中的全部示例可解析；非法语句报 `SQLSyntaxError` |
| B3 | 语义检查 | 查表/列、列数、类型与运算符适用性 | 错误在执行前报出，不产生半写入 |
| B4 | 计划选择 | 生成约定的六类 `Plan`，在索引等值条件下选 `index_eq` | 相同语句随索引有无产生不同 `access` |
| B5 | CLI | 交互输入、`.sql` 文件输入、结果表格、错误显示、正常退出 | 一条错误语句不使后续语句停止；结果含计划标签 |
| B6 | 文档与测试 | 用户使用说明、前端单元测试 | 未连接真实存储也能测试解析和规划 |

### B 的对外承诺

- `parse(sql)` 只做词法/语法解析；`plan(statement, storage)` 完成表列及类型检查，并返回纯数据计划。
- 表名、列名统一小写；字符串内容保留原样。`SELECT *` 在计划阶段展开为实际列名。
- B 只调用存储的 `get_schema`、`has_index` 等公开元数据方法，不检查磁盘文件。
- CLI 从 C 导入 `execute`，统一捕获 `DBMSError` 并呈现；不在前端重复实现行扫描。

### B 可独立验证的场景

写一个 `FakeCatalog`，只实现 `get_schema` 和 `has_index`：解析各类语句，比较 AST/Plan 字段；模拟索引存在/不存在，检查 `SeqScan`/`IndexEqScan` 选择。CLI 可暂用返回固定 `Result` 的假执行函数验证输入、输出和脚本分句。B 不需要等待页文件完成。

## 5. 成员 C：执行引擎与集成

### C 的细分任务

| 编号 | 任务 | 具体产物 | 完成判据 |
| --- | --- | --- | --- |
| C1 | 查询执行 | `SelectPlan` 的扫描、谓词判断、列投影 | 六种比较符和 `SELECT *` 结果正确 |
| C2 | 写操作执行 | 建表、建索引、插入、更新、删除计划的派发 | `affected_rows` 正确；无条件更新/删除覆盖全表 |
| C3 | 索引候选复核 | `index_eq` 时调用 `lookup_eq` 并再次判断谓词 | 假存储返回额外候选行时不会误报结果 |
| C4 | 遍历安全 | 更新/删除前物化匹配 `RowRef` 列表 | 修改索引时不漏行、不重复处理 |
| C5 | 集成 | 连接 B 的计划与 A 的存储，编写端到端测试 | 从 CLI 运行脚本，重启后查询结果正确 |
| C6 | 演示与报告 | `examples/demo.sql`、测试记录汇总、合并问题清单 | 能现场展示全表扫描、索引扫描、缓存与持久化 |

### C 的对外承诺

- `execute(plan, storage) -> Result`；不解析原始 SQL，也不打印结果。
- 仅调用存储层公开方法；`SelectPlan.columns` 已由 B 处理，C 按 schema 顺序定位列。
- 任何计划都返回约定的 `Result`，SELECT 给列名和行，写操作给影响行数。
- 合并失败时给出最小复现（SQL、预期、实际、错误位置），交给对应模块负责人修复；跨模块问题由 C 协调。

### C 可独立验证的场景

写一个内存 `FakeStorage`，实现 `scan`、`lookup_eq`、`insert`、`update`、`delete` 等同名方法；手工构造 `Plan`，测试过滤、投影、受影响行数和索引候选复核。C 不需要等待 B 的 parser 或 A 的文件实现。

## 6. 模块交接表

| 交接 | 提供方必须给出 | 接收方要验证 | 典型冲突及处理 |
| --- | --- | --- | --- |
| A → B | `get_schema`、`has_index`、约定异常 | 表列检查和索引选择 | 字段名/类型不一致：改 02 文档后两边同步 |
| B → C | 六类 `Plan` 及合法字段值 | 每类计划至少一个执行测试 | `columns` 是否展开、`access` 取值不一致：以 02 文档为准 |
| C → B | `execute` 和 `Result` | CLI 格式化、错误后继续 | 执行器打印或 CLI 计算结果：删掉重复逻辑 |
| A → C | `RID`、`RowRef` 的使用约定和写入方法 | 更新/删除索引一致性 | 更新引起 RID 变化：遵守 MVP 长度限制或先改接口 |
| 三人 → 集成 | 各自通过的测试与使用方法 | 演示脚本、重启、错误用例 | 记录最小复现和责任模块，修复后重跑相关用例 |

跨模块数据只走 02 文档中的公开类型和接口；禁止在另一模块里访问 `_pages`、私有索引字典、原始 heap 文件等实现细节。

## 7. 里程碑与合并顺序

以下是**相对阶段**，按课程截止时间自行填日期。每个阶段结束才进入下一阶段；不要等三人全部写完才第一次合并。

| 阶段 | A | B | C | 可运行检查点 |
| --- | --- | --- | --- | --- |
| M0 接口冻结（已完成） | 使用既定存储签名 | 使用既定语法与计划字段 | 使用既定共享类型 | 三个包能导入；契约文档一致 |
| M1 最小链路 | 建表、插入、全表扫描、关闭重开 | `CREATE TABLE`/`INSERT`/`SELECT` 解析、顺序扫描计划、最小 CLI | 三类计划执行、基础集成测试 | CLI 建表、插入、查询并重启验证 |
| M2 核心扩展 | LRU、索引、更新、删除 | 其余 SQL、索引计划、完整 CLI | 其余执行路径、索引复核 | 演示脚本完整跑通 |
| M3 稳定与提交 | 修复存储/缓存缺陷，写实现说明 | 补错误用例、用户说明 | 跑回归、汇总测试报告与贡献说明 | 干净目录一键运行、测试无失败 |

建议合并顺序：以现有 M0 共享类型为基线；M1 先 A 的最小存储、再 B 的解析计划、再 C 的执行连接；M2 各模块小步合并。每次合并后运行本模块测试和现有集成测试。若项目尚未初始化 Git，可以先 `git init` 并建立主分支；三人分别使用 `feature/storage`、`feature/frontend`、`feature/executor`，避免直接在同一份文件上相互覆盖。

## 8. 合并门槛与问题处理

每个模块提交合并时附四项信息：**改了什么、公开接口是否变化、测试命令与结果、已知限制**。代码不能只在作者电脑上运行；测试使用临时目录，不能写死本机绝对路径。

| 门槛 | 必须满足 |
| --- | --- |
| A 合入 | 存储 API 单测通过；关闭重开后表、行、索引一致；缓存统计可验证 |
| B 合入 | 六类语句解析/错误测试通过；有无索引的计划选择可验证；CLI 不吞异常 |
| C 合入 | 假存储上的执行测试通过；影响行数和结果字段正确 |
| 全部完成 | [04 测试与提交](04-testing-and-delivery.md) 的集成场景通过；演示脚本能在新目录运行；重启查询正确 |

发生接口分歧时，先贴出一条具体调用及其预期返回值，三人确认后**同步修改共享代码、02 文档和测试**。发生缺陷时记录：复现命令/SQL、预期、实际、所属模块、修复人、回归测试。不要在调用方加临时特判来掩盖提供方的契约错误。

若进度紧张，按如下顺序保交付：①建表、插入、查询、落盘重启；②缓存替换与持久化索引；③更新、删除及相关索引维护；④输入体验和可选增强。缩小范围前应更新 01 文档和报告，明确哪些功能实际完成。
